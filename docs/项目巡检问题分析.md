# 项目巡检问题分析

巡检时间：2026-06-13

本次范围覆盖 `src`、`electron`、`server`、`package.json`、`vite.config.mjs`、`docs` 与构建产物。已执行：

- `npm run lint`：通过，但只检查 Electron / backend 的 CommonJS 语法。
- `npm run build`：通过，但产物出现大 chunk 警告。
- 构建结果：主 JS `2,341.47 kB`，gzip `773.02 kB`；CSS `481.03 kB`，gzip `65.09 kB`。

## 总体判断

项目目前可以构建运行，但已经出现三类需要优先处理的问题：

1. 流程状态分散在页面、composable 和 store 中多处直接改写，已经产生可复现的流程错误。
2. Electron IPC 与本地文件能力缺少来源校验、路径校验和大小限制，安全风险较高。
3. 前端生产包全量加载，且透明悬浮窗口命中测试存在常驻高频轮询，性能压力明显。

## P0/P1 严重问题

### 1. 截图资源文件名存在路径穿越风险

位置：

- `server/sessionAssets.cjs:26-30`
- `server/sessionAssets.cjs:65-73`
- `electron/preload.cjs:3-10`
- `electron/main.cjs:96-98`

问题：

`saveScreenshotAsset()` 使用 renderer 传入的 `sessionId` 生成 `assetId`，再直接拼接到 `path.join(STORE_DIR, ...)`。`releaseScreenshotAsset(assetId)` 也直接使用外部传入的 `assetId` 拼路径删除文件。没有做字符白名单、`basename`、`path.resolve` 边界校验。

影响：

如果 renderer 被 XSS、非预期页面或恶意本地页面控制，可构造 `../` 逃出临时目录，写入或删除任意 `.png/.json` 路径附近的文件。这个风险会被 preload 的宽暴露面进一步放大。

建议：

- `assetId` 由主进程使用 `crypto.randomUUID()` 生成，`sessionId` 只放 metadata。
- 删除时只接受 UUID 格式 ID。
- 写入/删除前使用 `path.resolve` 校验最终路径必须位于 `STORE_DIR` 内。
- 文件写入改为异步 API，并统一捕获错误返回结构化结果。

### 2. IPC 能力暴露过宽，缺少 sender 来源校验

位置：

- `electron/preload.cjs:3-10`
- `electron/main.cjs:88-98`
- `electron/main.cjs:121-152`

问题：

preload 暴露了 `request(payload)`、截图、鼠标穿透、交互区域、退出应用等能力，但主进程 IPC handler 没有校验 `event.senderFrame.url`。窗口也没有拦截导航或新窗口打开。

影响：

只要开发端口被占用、页面被导航、或 renderer 出现 XSS，非预期页面就可能调用截图、本地文件保存/删除、退出应用、改变鼠标穿透区域等能力。

建议：

- 所有 IPC handler 统一校验 sender origin，只允许开发期 `http://127.0.0.1:5173` 和生产 `file://.../dist/index.html`。
- 增加 `webContents.on('will-navigate')` 和 `setWindowOpenHandler` 拦截。
- 避免通用 `request(payload)`，改为按业务能力暴露最小 API。
- `app:quit` 建议只允许可信页面触发，并增加业务确认或主进程侧保护。

### 3. 普通小屏期间浮球仍可能显示，违反流程约定

位置：

- `src/App.vue:39-41`
- `src/stores/flow.js:56`

问题：

项目约定“胶囊 / 悬浮球只在 `viewMode === 'idle'` 时显示”。但当前 `flowStore.shouldHideFloatingBall` 只隐藏 `fullscreen`、`compact`、`minimized`，没有隐藏 `small-page`。`App.vue` 也没有直接用 `viewMode === 'idle'` 判断。

影响：

`ask-entry`、`multi-question`、`read-recite`、`voice-question-*` 等普通小屏期间仍可能露出浮球。用户再次点击“问”可能重置当前业务流程和 session，造成状态覆盖。

建议：

`showFloatingBall` 直接以 `flowStore.viewMode === 'idle'` 为主条件。普通小屏需要定位锚点时，应使用 store 中的 `ballPosition`，不要依赖浮球可见。

### 4. 学生详情页最小化后无法恢复

位置：

- `src/views/ask/subjective/ReadReciteStudentAnalysisView.vue:160-164`
- `src/views/ask/subjective/VoiceStudentAnalysisView.vue:150-154`
- `src/components/widget/WidgetHost.vue:18-26`

问题：

两个学生详情页最小化时只调用 `flowStore.minimizeFullscreen()` 并 `router.replace('/')`，没有创建或保留 `widgetStore.activeWidget`。但 `WidgetHost` 只有在 `flowStore.viewMode === 'minimized' && widgetStore.activeWidget` 时才显示右侧恢复按钮。

影响：

页面进入 `minimized` 后，浮球被隐藏，恢复按钮也不显示，用户会进入不可恢复状态。

建议：

- 把全屏最小化统一收口到 `flowStore` / `widgetStore` action。
- 所有全屏页最小化都必须创建一个可恢复的 `activeWidget` 或独立 minimized task。
- 补齐 student-analysis 路由到最小化类型的映射。

### 5. 多题缩屏进入单题缩屏后，全屏目标错误

位置：

- `src/views/ask/composables/useMultiBatchAnalysis.js:252-255`
- `src/views/ask/composables/useObjectiveQuestionAnalysis.js:183-191`
- `src/components/widget/WidgetHost.vue:344-357`

问题：

多题缩屏中点击某题后，当前显示的是单题分析缩屏，但代码把 `flowStore.fullscreenRoute` 写成 `/ask/multi-batch-analysis`。随后单题分析 composable 在 `compactParent` 场景又继续把 full screen route 写回父级路由。

影响：

用户在单题分析缩屏点击“全屏”，会回到多题列表，而不是当前单题详情，当前题上下文丢失。

建议：

当前 widget 的全屏目标应保持 `/ask/objective-detail`。父级返回目标放在 `compactParent` 或 `returnTo` query 中，不要覆盖当前 widget 的全屏目标。

### 6. 首屏 bundle 单文件过大，没有代码分割

位置：

- `src/router/index.js:2-10`
- `src/components/widget/widgetRegistry.js`
- `src/main.js:3-4`
- `src/views/ask/MultiBatchAnalysisView.vue:231`
- `vite.config.mjs:11-14`

问题：

路由页全部静态 import，widget 注册表也静态 import 所有小屏/缩屏组件。Element Plus 和 CSS 全量引入，ECharts 使用 `import * as echarts`，Vite 没有拆包策略。

影响：

当前生产构建主 JS 达 `2.34 MB`，gzip 后仍有 `773 KB`。透明悬浮应用启动时会加载全部问业务、主观题、图表库和 Element 样式，影响启动速度、内存占用和热更新体验。

建议：

- 路由组件改为 `() => import(...)`。
- `widgetRegistry` 使用 `defineAsyncComponent` 或懒加载映射。
- Element Plus 改按需组件和样式引入。
- ECharts 改用 `echarts/core` 并只注册需要的图表和渲染器。
- `vite.config.mjs` 增加 `manualChunks` 和 bundle size budget。

### 7. 渲染进程和主进程常驻高频轮询

位置：

- `src/App.vue:45-82`
- `src/App.vue:152-156`
- `electron/main.cjs:33-58`
- `electron/main.cjs:166-169`

问题：

渲染进程每 `120ms` 查询 hitbox 和 `.el-popper`，读取 `getComputedStyle()` 与 `getBoundingClientRect()`，再 IPC 同步给主进程。主进程同时每 `50ms` 获取鼠标坐标并遍历交互区域。

影响：

即使页面无明显交互，也会持续产生 DOM 查询、布局读取、IPC 和主进程轮询。教室一体机大屏、透明 overlay、拖拽和动画场景下容易造成 CPU 占用、输入延迟和卡顿。

建议：

- 前端改为事件驱动，优先在弹窗打开/关闭、拖拽、resize、内容变化时同步。
- 使用 `ResizeObserver` / `MutationObserver` 做局部触发。
- idle、fullscreen 或无交互区域时暂停轮询。
- 主进程只在需要鼠标穿透时启动 hit testing，并限制 regions 数量和坐标范围。

## P2 中等问题

### 8. `route.query` 注释为真相源，但恢复时被旧 store 覆盖

位置：

- `src/views/ask/composables/useObjectiveQuestionAnalysis.js:145-173`

问题：

注释写明全屏页以路由 query 为准，但 `restoreAnalysisState()` 使用 `saved?.currentPage || pageFromQuery || 1`，旧的 `objectiveAnalysisState.currentPage` 优先级高于 URL 中的 `questionIndex`。

影响：

从多题列表进入某一题、刷新页面或恢复带 query 的详情路由时，可能展示上一次保存的题号。

建议：

全屏路由存在 `questionIndex` 时优先使用 query。store 只作为无 query 或缩屏 widgetProps 场景的 fallback。

### 9. 流程状态职责边界被打散

位置示例：

- `src/views/ask/ObjectiveQuestionDetail.vue`
- `src/views/ask/composables/useMultiBatchAnalysis.js:252-287`
- `src/views/ask/subjective/ReadReciteAnalysisView.vue`
- `src/views/ask/subjective/VoiceAnalysisView.vue`
- `src/stores/flow.js`

问题：

多处页面和 composable 直接写 `flowStore.currentStep`、`fullscreenRoute`、`viewMode`、`fullscreenQuery`，并自行 `router.push/replace`。这和“flowStore 负责决定下一步”的项目约定冲突。

影响：

已经表现为最小化丢恢复入口、缩屏全屏目标错误、query/store 优先级不一致。后续新增流程时会继续扩大状态分叉。

建议：

补充统一 action，例如：

- `openObjectiveDetail()`
- `openStudentDetail()`
- `minimizeFullscreenPage()`
- `shrinkFullscreenPage()`
- `returnToCompactParent()`

页面只提交业务意图并消费返回 target，不直接改流程字段。

### 10. `v-html` 渲染未做转义或净化

位置：

- `src/views/ask/subjective/components/AnswerProgressContentPanel.vue:21`
- `src/views/ask/subjective/VoiceAnalysisView.vue:98`
- `src/views/ask/subjective/ReadReciteAnalysisView.vue:18`
- `src/views/ask/subjective/widgets/ReadReciteAnalysisCompactWidget.vue:20`
- `src/views/ask/subjective/utils/buildAnswerProgressSession.js:9-18`
- `src/views/ask/subjective/utils/buildAnswerProgressSession.js:22-29`

问题：

`plainTextToHtml()` 和 `paragraphsToHtml()` 直接把文本插入 HTML 字符串，然后交给 `v-html` 渲染，没有 HTML escaping 或 sanitizer。

影响：

当前 mock 内容风险较低，但一旦接入真实教材、语音转文本、后端题干或用户自定义内容，就可能触发 XSS。Electron renderer 中的 XSS 会进一步放大 IPC 暴露风险。

建议：

- 纯文本优先用模板渲染，不生成 HTML 字符串。
- 必须渲染 HTML 时接入可信 sanitizer，并限制允许标签。
- `plainTextToHtml` 至少先转义 `& < > " '`。

### 11. 截图 base64 未限制大小，且同步写盘

位置：

- `server/sessionAssets.cjs:18-31`

问题：

`imageBase64` 未校验 MIME、base64 合法性和解码大小，且使用 `Buffer.from(..., 'base64')` 与 `fs.writeFileSync()` 在主进程同步执行。

影响：

异常大 payload 会阻塞主进程，可能耗尽内存或磁盘，导致应用卡死。

建议：

- 限制解码后图片大小。
- 校验 MIME 与 base64 格式。
- 改用 `fs.promises.writeFile`。
- 对错误返回结构化结果，不让异常冒泡到 IPC。

### 12. Electron 窗口隔离配置还不够完整

位置：

- `electron/main.cjs:78-82`

问题：

已启用 `contextIsolation: true` 和 `nodeIntegration: false`，但没有启用 `sandbox: true`。

影响：

preload 仍运行在带 Node 能力的环境中。在 preload/API 暴露较宽的情况下，安全边界偏弱。

建议：

补充 `sandbox: true`，并确认 preload 只暴露纯数据和最小函数。

### 13. backend 固定端口启动缺少错误处理

位置：

- `server/backend.cjs:74-93`
- `electron/main.cjs:160-163`

问题：

本地 HTTP server 固定监听 `127.0.0.1:17890`，没有监听 `error` 事件，也没有在 Electron 启动处 try/catch。

影响：

端口占用时应用可能启动失败或 Promise 悬挂，窗口不创建，错误不可诊断。

建议：

- `server.listen` 增加 `error` reject。
- Electron 启动流程加 try/catch。
- 端口可配置或允许 fallback。
- 如果当前只提供 `/health`，评估是否暂时移除 HTTP server。

### 14. mock 数据进入生产业务链路

位置：

- `src/views/ask/composables/useMultiBatchAnalysis.js:26-108`
- `src/views/ask/subjective/utils/buildVoiceAnalysis.js:1-8`
- `src/views/ask/subjective/utils/buildReadReciteAnalysis.js`
- `src/views/ask/subjective/utils/buildReadReciteSession.js:1-4`

问题：

生产源码直接 import `src/mock`，并把 mock 作为默认数据源和分析结果生成器。

影响：

正式构建会携带 mock 数据。真实数据为空时页面仍可能显示 mock，容易误判业务状态，也会增加包体积。

建议：

将 mock 封装为 development-only adapter 或 fixture 层，通过环境变量隔离。正式路径缺数据时显示空态。

### 15. 质量门禁几乎没有覆盖前端

位置：

- `package.json:10-12`
- `tests/`

问题：

`npm run lint` 只执行 `node --check`，不检查 Vue SFC、前端 JS、SCSS、未使用依赖、路由懒加载、组件边界等。仓库没有 `test` 脚本，`tests` 目录为空。

影响：

流程 store、utils、组件交互和样式回归都不能被本地命令拦截。

建议：

- 加入 ESLint 和 `eslint-plugin-vue`。
- 加入 Vitest，优先覆盖 `flowStore`、`smallPageStore`、`widgetStore`、`answerDistribution`、截图资源工具。
- 增加 `npm run check`，组合 lint、test、build。
- 加入 bundle size 检查。

## P3 低优先级但建议整理

### 16. 构建期依赖放在 runtime dependencies

位置：

- `package.json:22-30`

问题：

`@vitejs/plugin-vue` 和 `sass` 是构建期依赖，却放在 `dependencies`。

建议：

移动到 `devDependencies`，减少生产安装和打包依赖体积。

### 17. 全局样式和 Element 覆盖作用面偏宽

位置：

- `src/style/common.scss:35-64`
- `src/style/element.scss`

问题：

全局 `button` reset、`.overlay-root > * { pointer-events: auto; }`、全局 `.el-button` 覆盖、`.el-popper` 超高 z-index 等选择器作用面较宽。

影响：

后续新增页面或 Element 组件可能被非预期影响。所有 popper 都顶到最高层级，也会增加截图层、业务弹层和系统交互层的调试难度。

建议：

全局只保留 token/reset。Element 覆盖尽量用 CSS 变量或限定业务容器 / `popper-class`，避免无差别覆盖。

### 18. store 模块初始化阶段直接访问 `window`

位置：

- `src/stores/smallPage.js:89-95`
- `src/stores/widget.js:47-88`

问题：

store 文件在模块初始化和 action 中直接访问 `window.innerWidth/innerHeight`。

影响：

当前 Electron renderer 可以运行，但会降低单元测试、SSR 或 Node 环境导入的兼容性。

建议：

把窗口尺寸读取收敛到 action 参数或工具函数中，并为非浏览器环境提供 fallback。

## 建议修复顺序

1. 先修安全底座：IPC sender 校验、导航拦截、截图资源路径校验、base64 大小限制。
2. 修复流程硬 bug：普通小屏隐藏浮球、学生详情最小化恢复、多题缩屏单题全屏目标。
3. 收敛流程状态：新增 flowStore actions，禁止页面/composable 直接改写流程核心字段。
4. 降低性能压力：路由和 widget 懒加载，Element/ECharts 按需，命中测试改事件驱动。
5. 补质量门禁：ESLint、Vitest、bundle size 检查和 `npm run check`。
6. 清理 mock 和依赖边界：mock 开发期隔离，构建期依赖移入 devDependencies。
